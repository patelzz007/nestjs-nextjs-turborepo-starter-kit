# `@workspace/mobile` — the Expo app

The starter's iOS and Android app: Expo SDK 57 (React Native 0.86, React 19.2), Expo Router,
Uniwind on Tailwind v4, TanStack Query / Form and Zustand feature stores, all in strict TypeScript.
It is a **generic starter shell**, not a product: sign-in with every step the API can ask for
(password → authenticator or backup code → emailed new-device code), forced 2FA enrollment, sign-up,
password-reset request, Home, Profile, Settings (appearance, security, signed-in devices, app lock,
about, sign out) and the blocking update and configuration-error screens. It talks to the NestJS API
as client type `mobile` with tokens in JSON bodies, kept in the OS secret store.

The full design, and why each choice was made: [`docs/technical/mobile/mobile-app.md`](../../docs/technical/mobile/mobile-app.md)
(sections 9–11, 15).

```

eslint.config.mjs    @workspace/eslint-config/react-native + the env boundary

    _layout.tsx      root layout: stylesheet, app runtime, root guard
    config-error.tsx, update-required.tsx, lock.tsx
    (auth)/          sign-in, verify-device, two-factor, sign-up, forgot-password, enroll-two-factor, verify-email
    (app)/           tabs: index (Home), profile, settings/ (index, appearance, security, devices, app-lock, two-factor)
  components/        presentational: data-agnostic, controlled, accessible, token-styled
  features/          session (root guard state machine), preferences (theme, app lock settings), app-lock,
                     auth (login steps, sign out, refresh), two-factor (enrollment flow), devices, profile
  lib/               env, api client, Secure Store registry + token provider, app version, device headers,
                     query client, error messages, the feature-store toolkit (lib/state)

  app-tests/         the route screens' tests, mirroring src/app — NEVER put a file other than a

```

## Getting started

### One-time setup

1. Install the repo (`pnpm install` at the root) and set up the API as the root README describes.
2. Create (or reuse) a **free Expo account** at expo.dev. No paid plan, no EAS, no store accounts.
3. Install **Expo Go** from the App Store / Google Play on each test phone and sign in to it with
   that account (Expo Go requires a signed-in account on SDK 57).
4. Sign in on the dev machine too: `npx expo login` (from `apps/mobile`).
5. Put the phone and the dev machine on the **same network** (the phone loads the bundle and calls
   the API over it).
6. Let the API accept connections from the phone: set `HOST=0.0.0.0` in `apps/api/.env` and
   restart it. The API's default bind address, `127.0.0.1`, only accepts connections from the dev
   machine itself, so a phone's requests are refused (the Android emulator alone gets through, via its
   `10.0.2.2` alias). This exposes the dev API to your local network; use a trusted network.
7. Optional: `cp apps/mobile/.env.example apps/mobile/.env`. In development nothing else is
   required — the app finds the API by itself.

### Daily loop

```bash
pnpm dev:api        # the API on :8080 (in one terminal)
pnpm dev:mobile     # Expo / Metro for the app (in another)
```

Scan the QR code Expo prints: with the **Camera** app on iPhone, with **Expo Go** on Android. The
app reaches the API at `http://<the dev machine's address Expo Go connected to>:8080` — never
`localhost`, which on a phone is the phone. If your API listens elsewhere, set `EXPO_PUBLIC_API_PORT`
(or `EXPO_PUBLIC_API_URL` for another machine) in `apps/mobile/.env` and restart Expo. With
`expo start --tunnel` (a network that blocks LAN traffic) the phone cannot reach the API through the
dev machine's address: set `EXPO_PUBLIC_API_URL` to an address the phone can reach.

### Commands

| Command | What it does |
| --- | --- |
| `pnpm --filter @workspace/mobile dev` | `expo start` (same as `pnpm dev:mobile` from the root) |
| `pnpm --filter @workspace/mobile lint` | ESLint, zero warnings |
| `pnpm --filter @workspace/mobile typecheck` | `tsc --noEmit` with the repo's strict flags |
| `pnpm --filter @workspace/mobile test` | jest-expo suites, then `expo install --check` (SDK version drift fails) |
| `pnpm --filter @workspace/mobile build` | `expo export --platform ios --platform android` into `dist/` — the CI bundle check (no Xcode / Android Studio needed) |

### Adding a dependency

- **Expo-managed** (anything `npx expo install` knows — expo-*, react-native-*, React itself):
  `cd apps/mobile && npx expo install <package>`. Never `pnpm add` them: the SDK pins their versions
  and `expo install --check` fails on drift.
- **Everything else**: `pnpm --filter @workspace/mobile add <package>@<latest stable>`.
- Only modules **Expo Go includes** may be used (no custom native code) while the app develops in
  Expo Go. AsyncStorage is banned outright (lint): persist through `src/lib/secure-store.ts`.

### Upgrading the Expo SDK

Each Expo Go build runs exactly one SDK. When Expo releases the next SDK as **stable** and ships it
in Expo Go (betas need a private TestFlight build of Expo Go and an Apple Developer membership):

1. `cd apps/mobile && npx expo install expo@<next> --fix` (realigns every Expo-managed package).
2. Update the `apps/mobile` version groups in `.syncpackrc.json` (React, `@types/react`,
   React Native and `@react-native/*`, Metro, Jest) to what the new SDK pins — `expo install --check`
   and `pnpm deps:check` tell you what is off.
3. Re-check `jest-expo` / `@react-native/jest-preset` / `@testing-library/react-native` compatibility
   and Uniwind's supported React Native range.
4. Run the full gate (`pnpm run lint`, `pnpm run test`, `pnpm run typecheck`, the mobile `build`),
   then test on a real iPhone and a real Android phone.
5. Update the version references in `docs/technical/mobile/mobile-app.md` and `rules/04-mobile-expo.md`.

## Key conventions

- Mobile rules and the decisions behind them: [`rules/04-mobile-expo.md`](../../rules/04-mobile-expo.md)
  (read its first section), and the non-negotiables in [`rules/00`](../../rules/00-non-negotiables.md),
  [`rules/27`](../../rules/27-array-index-readability.md), [`rules/28`](../../rules/28-runtime-validation.md).
- Tests: jest-expo, the one exception to Vitest — [`rules/11`](../../rules/11-testing-vitest.md#the-one-exception-to-vitest-appsmobile-uses-jest-expo).
  Screens are tested inside Expo Router's test router with the real runtime (`renderInApp`); only
  `fetch` and native modules are faked.
- Styling: Uniwind token utilities only ([ADR 032](../../docs/adr/032-uniwind-for-mobile-styling.md));
  tokens come from `packages/tokens` (`pnpm tokens:generate`), never edited here.
- Third-party components ignore `className` until wrapped with `withUniwind` (see
  `src/components/screen.tsx`). Nothing warns, and Jest renders without styles, so check a new
  third-party component on a device or in Expo Go.
- API: only through `@workspace/api-client` (token transport, [ADR 029](../../docs/adr/029-mobile-client-body-token-transport.md));
  `@workspace/client` and `@workspace/ui` are web-only and lint-banned here.
- Navigation: screens report what happened to the session (`useSessionCommands()`); the root guard
  moves the app. Route params are parsed with zod (`useRouteParams`).
- Where code goes (app vs shared package): [`rules/01`](../../rules/01-repository-architecture.md).

## Environment variables

`EXPO_PUBLIC_*` values are bundled into the app and are **public** — never put a secret there.
Details: [`docs/technical/configuration/frontend.md` §10](../../docs/technical/configuration/frontend.md#10-the-mobile-app-appsmobile).

| Variable | Purpose | Required |
| --- | --- | --- |
| `EXPO_PUBLIC_API_URL` | The API's absolute URL (`https://` outside development) | Outside development |
| `EXPO_PUBLIC_API_PORT` | Development: the API's port on the dev machine (default `8080`) | No |
| `EXPO_PUBLIC_IOS_STORE_URL` / `EXPO_PUBLIC_ANDROID_STORE_URL` | Store pages for the update screen | No |
| `MOBILE_APP_NAME` | Display name (default `Starter`) | No |
| `MOBILE_APP_SLUG` | Expo slug (default `starter`) | No |
| `MOBILE_BUNDLE_ID` | iOS bundle id and Android package (default `com.example.starter`) | No |
| `MOBILE_SCHEME` | Deep-link scheme (default `starter`) | No |

### Configuration

If the environment is invalid (for example a release bundle without `EXPO_PUBLIC_API_URL`, or an
`http://` URL outside development), the app opens on the **configuration error** screen, which names
the variable and shows an example value. Fix `apps/mobile/.env` (or the build environment) and
restart Expo / rebuild.

## Expo Go limitations

| Limitation | Effect here |
| --- | --- |
| No Face ID in Expo Go (iPhone) | The app lock uses the **device passcode** instead. Expected, not a bug; a real build uses Face ID (`faceIDPermission` is set in `app.config.ts`). Android uses fingerprint / face as enrolled. |
| No remote push notifications | Push is out of scope |
| No universal / app links | Email links (verification, password reset) open the web pages |
| No custom native modules | Only modules Expo Go ships are used |
| Icons and splash screens are Expo Go's | Verify them in a real build |
| Simulators/emulators | Biometric enrollment is simulated; check the app lock on real phones |

App-lock limits worth knowing: "biometrics changed" is detected from what `expo-local-authentication`
exposes (the enrolled security level and authentication types). It notices biometrics being
removed, switched (fingerprint ↔ face) or the passcode being removed — **not** an extra finger or
face added to the same enrollment (that needs native keystore invalidation in a real build). The
privacy cover is drawn when the app becomes inactive; on Android the recents snapshot may be taken
before it paints — a real build can add `FLAG_SECURE` (`expo-screen-capture`) if that matters.
