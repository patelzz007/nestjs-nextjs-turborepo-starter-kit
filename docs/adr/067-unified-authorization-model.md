# ADR 067: One authorization model — roles, grants, shares, ownership and RLS

## Status

**Accepted; Phases 1–3 built, Phase 4 partly built (2026-10-28).** Every decision below was agreed in a
design interview (the Q&A trail is [at the end](#the-decision-trail)) and refined by two external
reviews. Phase 4 removed Cedar, the JSON policy engine, `MANAGE` and role inheritance; what it has not removed yet is listed under
[As built (Phase 4)](#as-built-phase-4). Supersedes the authorization parts of
[ADR 026](./026-kernel-first-authorization.md) once Phase 4 lands.

### As built (Phases 1 and 2)

Where the code differs from the plan below, the code is right and this list says why:

- **No data command.** The owner resets the database and reseeds, so nothing needs moving: the seed
  writes the new shape directly (tenant copies of the templates, `roleId` on every membership, the
  platform Manager's holders as Admins). The planned `pnpm tools authz:migrate` was not built.
- **`Role.templateKey`** (the template's tenant role, `OWNER` / `MANAGER` / `CASHIER`) instead of
  `templateRoleId`: a tenant copy names *which* template it is, which is what reset and the Owner
  guardrails need. `Role.kind` is `PLATFORM`, `TEMPLATE` or `TENANT`; role names are unique per tenant
  among live roles.
- **Kept until Phase 4, read by nothing new:** the `Membership.role` enum (mirrored from the role's
  template; a custom role mirrors `CASHIER`), `UserPermission.effect` and `ResourceAcl.effect` (DENY
  rows are ignored), `OWN` / `RESOURCE` scoped permission rows (ownership and shares say that now),
  `MANAGE` (still implies every action, in the API and in RLS alike), role inheritance, the Location
  Manager / Location Staff roles and Cedar.
- **Decision service:** `AccessControlService` (`contexts/authorization/application/services`), built
  from four allow-path strategies in `domain/access/`; other contexts reach it through
  `AccessControlPort` and the `ACCESS_CONTROL` token. The kernel is a facade over it; a store the request
  was verified for (`?locationId=`) limits the decision to that store.
- **Tenant administration:** `TenantAccessService` and `/tenants/:tenantSlug/access/*`
  (`TenantAccessController`) — one service with a template-method skeleton (resolve tenant → decide →
  one transaction with its audit row) rather than one CQRS command per operation; the guardrails are pure
  functions in `domain/access/tenant-access.policy.ts`.
- **RLS:** `prisma/rls/02-access-model.sql` adds `app_has_permission(resource, action, tenant, store)` and
  `app_shared(resource, id, level)`; rewards, claims (merchant side), redemptions, shares and tenant roles
  use them. Rewards are tenant-level in RLS (a reward can sit in several stores); the API applies stores.
- **Shareable records** are rewards only (`ShareableResourceSchema`); a new type is one enum value and
  one `recordStores` case.

### As built (Phase 4)

**Removed (one generated migration, `…_adr067_phase4_retire_cedar_and_json_policies`):**

- Cedar: the engine (`@cedar-policy/cedar-wasm`), templates, policy bundles and their cache and
  cross-instance invalidation, drafts, simulation, publishing and their `/policies/*` routes, the
  default tenant policy provisioned with every tenant, the seeded guardrail and policy revision, and
  the tables `AuthorizationPolicyDraft`, `AuthorizationPolicyVersion`, `AuthorizationPolicySimulation`.
- The policy version everywhere it travelled: `TenantAuditLog.policyVersion`, the `app.policy_version`
  session setting, the signed job context, the tenant context response (and the merchant dashboard
  tile that showed it).
- The JSON condition engine: `PolicyDefinition`, `Permission.conditions`, `ResourceAcl.conditions`,
  the condition language in `@workspace/shared`, and the kernel's dead collaborators
  (`SubjectGrantsLoader`, `AclService`, `PolicyEngineService`, `ResourceOwnershipResolver`).
- The fixed merchant role table (`MERCHANT_ROLE_CAPABILITIES`) was already gone; its last mentions went.

**Then removed (migration `…_adr067_phase4_retire_manage_and_role_inheritance`, generated by
`prisma migrate diff` because Prisma's interactive `migrate dev` refuses to drop an enum value
non-interactively):**

- **`MANAGE`.** Every route that required it now names the verb it performs, and every role that held
  it holds exactly those verbs, so nobody gained or lost access:

  | Routes | Now requires |
  |---|---|
  | merchant invite, slug availability, invite email preview | `CREATE MERCHANT_ORG` |
  | KYB decision, store-request review | `APPROVE MERCHANT_ORG` |
  | add a store to a merchant | `UPDATE MERCHANT_ORG` |
  | suspend / reinstate / reject an appeal | `SUSPEND` / `REACTIVATE` / `REJECT MERCHANT_ORG` |
  | ban / lift a ban (still `@SuperAdminOnly`) | `BAN` / `UNBAN MERCHANT_ORG` |
  | reward moderation queue, detail, image downloads, approve | `APPROVE REWARD` |
  | reject a reward | `REJECT REWARD` |
  | rearrange the kanban columns | `UPDATE KANBAN_BOARD` (a new resource: the board's layout is not a task) |
  | platform staff into the merchant portal | `UPDATE MERCHANT_ORG` |

  `permissionSatisfies`, the kernel, the holders read, RLS `app_has_permission` and the client's `can()`
  all match the exact verb.
- **Role inheritance.** `Role.parentId`, the reparent command and its `PATCH /admin/roles/:id/parent`
  route, the cycle check and every ancestor / descendant walk are gone. Roles are flat: a role that
  should hold another's permissions lists them (the seeded *Support Agent* does). A change to a role
  reaches exactly its holders.

**Not removed yet:** the legacy columns — `Membership.role` (the mirror), `UserPermission.effect`
(platform DENY overrides still work), the legacy `ResourceAcl` columns, `OWN` / `RESOURCE` scopes,
`MembershipLocationScope.roleId` and the Location Manager / Location Staff roles.

## Requirements

The model must guarantee, with as little code as possible and every edge case covered:

1. **Tenant A can never see Tenant B's data.**
2. **A Cashier cannot see Manager-level data** without the necessary permission.
3. **User A cannot see User B's data** (the customer web app, `localhost:3000`).
4. **Extra permissions for one person**, temporary (for example 48 hours, then revoked automatically)
   or permanent, on top of their role.
5. **Roles are editable:** permissions can be added to and removed from roles.

Plus: per-record sharing (ACL) is kept and given a real use, and RLS is the main enforcer.

## Principles

- **Less is more.** One mechanism per concern; reshape existing tables instead of adding parallel ones.
- **Deny by default.** Nothing is allowed unless one of the four allow paths says so.
- **The database is the main enforcer.** RLS decides which rows exist for a request; the API checks
  too, and both are tested independently.
- **Generic.** Nothing in the model knows about rewards, cashiers or Malaysia: those are data and seed.
- **SOLID, no duplication.** One decision service, one ownership registry, one audit event shape.

## The model

### One catalogue, one role model

- **Permissions** are one catalogue for the platform and every tenant, written `noun.verb`:
  - **Nouns** are singular (`reward`, `member`, `role`, `location`). Compound nouns are allowed
    and written with an underscore (`api_key`, `support_access`, `customer_ban`).
  - **Verbs** are CRUD — `create`, `read`, `update`, `delete` — where `read` also covers lists,
    plus the **closed** list of lifecycle verbs below. There is **no wildcard** (`MANAGE` goes).
- **Roles** are rows, scoped to the platform (`tenantId = null`) or to one tenant. A role is a set of
  permissions. Role inheritance (`parentId`) is not used by the new model.
- **Platform roles:** the `isSuperAdmin` flag (audited bypass, unchanged), **Admin** (platform staff)
  and **User** (every sign-up; User A and User B). The platform **Manager** role goes.
- **Tenant roles:** **Owner**, **Manager**, **Cashier**. Platform-level *templates* define them; each
  tenant gets its own **copy** when it is created. The tenant edits its copy; a template change
  reaches new tenants only, and a tenant can **reset a role to its template**.

### Lifecycle verbs (closed list)

A state change that is not a plain edit gets its own verb, so the person who can fix a typo
(`reward.update`) cannot also take something off sale. The list is derived from the transitions the
code has today and is **closed**: adding a verb is an amendment to this ADR. No `update` carries an
`action` field — that would be the rule engine again.

| Noun | Lifecycle verbs | Who uses them today |
|---|---|---|
| `reward` | `publish`, `approve`, `reject` | merchant publishes; platform reviews |
| `kyb` | `approve`, `reject` | platform reviews a tenant's verification |
| `location` | `approve`, `reject` | platform reviews a store request |
| `access_request` | `approve`, `reject` | tenant reviews a join request |
| `support_access` | `approve` | tenant Owner approves platform support |
| `tenant` | `suspend`, `ban`, `unban`, `reactivate` | platform acts on a whole tenant |
| `user` | `ban`, `unban`, `unlock` | platform acts on a person's account |
| `claim` | `redeem` | the POS redeems at the till |

Three "stop working" ideas exist and are kept distinct by their **noun**, never by near-synonym verbs:

- a **tenant** is suspended or banned (`tenant.suspend`, `tenant.ban`): platform action;
- a **user account** is banned (`user.ban`): platform action, the person can no longer sign in;
- a **membership** is suspended or ended: today only the tenant lifecycle does this; there is no
  per-member suspend verb (see [known gaps](#known-gaps)).

Revoking a key, invite or session is a soft delete: `api_key.delete`, `invite.delete`, `session.delete`.

### The four allow paths

A request is allowed when **any** of these allows it — and only then. There is no explicit DENY.

| Path | What it can satisfy | Delegable? | Expiry | Scope |
|---|---|---|---|---|
| **Role** | every permission in the member's (or platform user's) role | — | none (edit the role) | the member's stores |
| **Grant** | one extra permission for one member | **no** | optional end time, checked on every request | the tenant, or one store — intersected with the member's stores |
| **Share** | `view` (= read) or `edit` (= read + update) on **one record** | **no** | optional end time, checked on every request | that record only |
| **Ownership** | **read and update on a record the user owns** — never delete, never a lifecycle verb, never another record | — | none | that record only |

Ownership is **the one implicit allow path**: it is not stored as a grant. It is deliberately narrow.

Every decision records **which path allowed it** (or that none did) in the explain result and the
audit row, and the e2e tests assert the path, not only "allowed".

### Delegation: grants and shares cannot be passed on

- A member may grant permission **P** for store scope **S** only if **P is in their role** and
  **S ⊆ their own stores for P**. A wider grant is rejected when it is made, never stored inert.
- A member may share a record only at a level **their role** gives them on it (`view` needs
  `reward.read`, `edit` needs `reward.update`), and only with members of **the same tenant**.
- A permission held only through a grant or share can never be granted or shared onward. There are
  no delegation chains, so no cascading revoke, no inherited expiry and no cycles.
- A grant row stores who granted it, when, and the **role name they held at that time**. A grant can
  **outlive its issuer's authority**: if the issuer later loses the permission, the grant stays. This
  is a decision, not an accident; revoking it is a deliberate act.

### Undo your own (one principle)

- You can **always** revoke a grant or take back a share **that you made yourself** — even if your role
  has since lost the permission that let you make it.
- You can revoke or take back **someone else's** only with `member.update` (grants) or
  `share.delete` (shares). Owner and Manager hold both by default.

### Store scoping (ReBAC)

| Member's stores | Grant / share | Effective |
|---|---|---|
| "All stores" | tenant-wide | every store of the tenant **at request time**, including stores added later |
| "All stores" | store X | store X |
| {A, B} | tenant-wide | {A, B} |
| {A, B} | store A | A |
| {A, B} | store C | **nothing** (rejected at grant time; inert if the member later lost C) |

- Effective scope is **grant ∩ membership**, evaluated on every request. It is never copied into the
  token or the session, so "stores added later" and "store removed" are always current.
- Shrinking a member's stores **never edits or deletes** grant or share rows. A grant for a store they
  no longer cover is inert, and works again if that store is added back.
- Stores are **soft-deleted** (the repo rule). A deleted store's grants and shares become inert; the
  store foreign key is `ON DELETE RESTRICT`, so a hard delete can never null it into "all stores".

### Ownership and records with two parties

- A record with an owner column (`userId`) is readable and updatable by its owner, and by nobody else
  through ownership. **RLS is the main enforcer**; the API checks too.
- A record that belongs to a user **and** a tenant (a claim: User A's voucher at Brew & Bean) is visible
  to **its owner OR to members of that tenant who hold the permission for that store**. Never to
  another user, never to another tenant.

### Per-record sharing (the ACL)

- The existing `ResourceAcl` table is **reshaped** into the share table — no second table: a share is
  `(tenantId, resourceType, resourceId, granteeMembershipId, level VIEW | EDIT, expiresAt?, sharedBy,
  sharedAt)`. The DENY effect, conditions and role subjects go.
- **Rewards** are the first shareable record. The mechanism is generic: another record type becomes
  shareable by registering its noun, without a new table.

### Lifecycle and suspension

1. **Tenant suspended or banned:** the existing tenant lifecycle check runs **first**, unchanged, and
   refuses the tenant's members before anything else is evaluated. **Customers still see their own
   records** from that tenant (ownership is not membership).
2. **Membership suspended or ended:** every role, grant and share the member holds in that tenant stops
   at once, because every check goes through an **active** membership. Nothing has to be cleaned up.
   On rejoining they start from their new role only; old grants and shares do not come back.
3. **User account banned:** the person cannot sign in; they see nothing.

### Guardrails (fixed code, not rules)

- The **Owner role** cannot be edited or deleted; it always holds every tenant permission.
- A tenant always keeps **at least one Owner**.
- **Only an Owner** can make someone else an Owner.
- **Deleting a role that members still hold is refused:** `DELETE /roles/{id}` answers `409` with the
  holder list. `POST /roles/{id}/reassign` takes a full member → new role mapping plus the version of
  that holder list, applies it in **one transaction**, and fails with `409` if anyone joined or left
  the role in between. No member is ever moved to a default role.

### Platform staff and tenant data

- **SuperAdmin** keeps its audited bypass.
- Every other platform Admin reads a tenant's data **only through support access**: requested by the
  platform, **approved by an active Owner** of that tenant, time-limited and audited. A tenant with no
  active Owner can only be reached through the SuperAdmin's audited bypass.
- Support access and the SuperAdmin bypass write **one audit event type** (who, when, tenant, reason,
  before, after), so the audit screen has one renderer.

### Audit

- Every role edit, grant, revoke, share, unshare and reassignment is written **by the command that
  makes it**: who, when, before and after, and the allow path where a decision is involved.
- **Expiry is never written as a future-dated audit row.** The audit screen *shows* "expired at T"
  from the stored end time (a projection). When the tidy-up job later archives an expired row, it writes
  an `archived` audit row timestamped **when it runs** — a fact about the archiving.
- Audit timestamps are therefore always ≤ now.

### Expiry

Grants and shares are both evaluated against **now** on every request. The tidy-up job only archives
old rows; it never decides access. One expiry rule, one bug class.

### Data migration

*Not built — the database is reset and reseeded instead (see [As built](#as-built-phases-1-and-2)). The
mapping below is what the seed now writes.*

Prisma's generated migrations change the schema only, and migrations are never hand-written here
(`rules/08`). Moving existing data was to run as a one-off `pnpm tools` command (like the existing kanban
conversion), writing **one audit row per moved member**, as a system actor:

- tenant `OWNER` → Owner; tenant `ADMIN` and `POLICY_ADMIN` → **Manager**; `MEMBER` and `CASHIER` → **Cashier**;
- platform **Manager** holders → **Admin** (nobody loses access silently; the seed's
  `manager@example.com` and `david.lee@example.com` move with them);
- today's per-user `UserPermission` rows → grants (ALLOW rows only; there are no DENY rows to carry, and
  the model has no DENY).

## Phases

Each phase passes `pnpm lint`, `pnpm typecheck`, `pnpm test` and the API e2e suites before the next
starts. **Phases 1 and 2 are built together, then work stops** so the owner can re-migrate and run RLS.

### Phase 1 — schema and data (built with Phase 2)

- `schema.prisma`, reshaping instead of adding:
  - `Role`: `tenantId` (null = platform), `templateRoleId` (the template a tenant copy came from).
  - `Permission`: the `noun.verb` catalogue — CRUD plus the closed lifecycle verbs; `MANAGE` removed.
  - `Membership`: a `roleId` replaces the fixed `MembershipRole` enum; store scope stays in
    `MembershipLocationScope` (with "all stores" kept).
  - `UserPermission` → the **grant** table: adds `tenantId`, `locationId?`, `grantedVia` (role name at
    grant time); `effect` goes; `expiresAt` stays.
  - `ResourceAcl` → the **share** table, as described above.
  - Store foreign keys on grants and shares: `ON DELETE RESTRICT`.
  - Old tables the new model no longer reads (policy definitions, Cedar policy versions) are **kept**
    until Phase 4, so nothing breaks mid-way.
- One **generated** migration (`pnpm db:migrate:create`), never hand-written.
- The one-off data command (`pnpm tools authz:migrate`), with its audit rows and tests.
- The seed rewritten for the new model, seeding every column.

### Phase 2 — API decisions and RLS (built with Phase 1)

- **One decision service** answers "may this subject do `noun.verb` on this target?" from the four
  paths, returning the allow path. It replaces the kernel's precedence code, the merchant capability
  table and the Cedar check; `@RequirePermission` and the merchant gate both call it.
- **One ownership registry**: each owned record type declares its owner column once; the API check and
  the RLS policy both read from it.
- **RLS rewritten** around four SQL helpers mirroring the four paths (role, grant, share, owner), plus
  the tenant and store predicates; tenant-and-user records use "owner OR member with permission and store".
- Endpoints: tenant roles (CRUD, reset to template, reassign), grants (create, revoke), shares (create,
  delete), member role change and member removal (both missing today).
- The guardrails, the "undo your own" rule and the unified audit event.
- The 46-case edge matrix, through the API and against RLS.
- **Then stop.** The owner resets the database, migrates, seeds and applies RLS on their machine
  (`prisma migrate reset`, `pnpm db:seed`, `pnpm db:apply-security`); the e2e suite
  (`test/tenant-access.e2e-spec.ts`) shows the rules hold through the API and as `app_runtime`.

### Phase 3 — screens

- **Merchant → Team:** a Roles tab (tick permissions per role, reset to template, delete with the
  reassign prompt) and, on each member, "Extra permissions" with 24 h / 48 h / 7 days / custom /
  permanent and a store picker.
- **Merchant → a reward's page:** Share — person, view/edit, duration.
- **Admin → Access control:** platform role templates and platform roles.
- Built from the existing UI kit; every temporary grant or share shows its remaining time
  ("expires in 47 h"); the audit screen shows expiry as a projection.

### Phase 4 — remove the old code

- Cedar (the engine, templates, drafts, simulate, publish and their endpoints), the JSON policy engine
  and `PolicyDefinition`, the fixed `MERCHANT_ROLE_CAPABILITIES` table, the `MANAGE` handling and role
  inheritance, with a generated migration dropping the unused tables.
- The authorization docs rewritten against the final code.

## Rejected alternatives

| Alternative | Why not |
|---|---|
| Per-tenant permission catalogues | Tenants would invent incompatible permissions the code cannot check. One catalogue, per-tenant roles. |
| Explicit DENY | A second precedence rule to reason about. Restricting one person means giving them a different role. |
| Keeping Cedar (or a lighter policy language) | Every job it does is covered by roles, store scoping and three guardrails. Two deciders for one question can disagree — a security bug waiting to happen. |
| The JSON condition engine | No screen, three demo rules. Conditions that matter are plain code checks. |
| Delegable grants | Delegation chains need cascading revoke, transitive expiry and cycle rules. Can be added deliberately later. |
| A `MANAGE` wildcard | A grant should mean exactly what it says. |
| An `action` field inside `update` | That is a rule engine in disguise; lifecycle verbs are explicit. |
| Template changes flowing into tenant roles | What an Owner sees would not be what applies. Copies plus "reset to template" are explicit. |
| Materialising a member's stores into the token | Breaks "stores added later" and "store removed". |
| Future-dated audit rows for expiry | Breaks every consumer that assumes audit timestamps ≤ now. |

## Known gaps

- **No user account can be deleted.** There is no "delete my account" endpoint and no admin endpoint
  that deletes a user row; `user.ban` stops sign-in but keeps the row. `user.delete` is reserved in the
  catalogue for when that feature is built as its own task.
- **Members cannot be removed or have their role changed by an Owner today.** A member can leave
  (`members/me/leave`) and lose a store (`…/locations/:id/remove`), but there is no remove-member or
  change-role command. **Phase 2 adds both**, because the reassign guardrail needs them.
- **No per-member suspension.** A membership becomes suspended only through the tenant lifecycle.
  Adding `member.suspend` would be an amendment to the lifecycle-verb list.

| Q20 | Screens? | Team roles and member grants, reward Share, admin Access control |
| Q21 | Proof? | One named test per requirement and edge, through the API and RLS |
| Q22 | Delivery? | Phases 1 and 2 together, stop; then screens; then removal |
| Q23 | Member leaves or is suspended? | Everything stops at once; nothing returns on rejoin |
| Q24 | Deleting a held role? | Refused; the Owner is prompted to reassign; no default role |
| Q25 | Store removed? | Grants and memberships stop matching |
| Q26 | Tenant suspended? | Lifecycle check first, unchanged; customers keep their own records |
| Q27 | Audit? | Written by the commands; expiry shown from the end time |
| Q28 | Delegation? | Non-delegable; grant only what your role gives, within your stores |
| Q29 | Store ∩ grant? | Intersection, evaluated per request, rows never mutated, reactivation tested |
| Q30 | What ownership allows? | Read and update on that record only |
| Q31 | Support access approver? | Active Owner; no Owner → SuperAdmin bypass only |
| Q32 | Platform Manager holders? | Moved to Admin, each move audited |
| Q33 | Non-CRUD state changes? | CRUD plus a closed lifecycle-verb list, pinned per noun |
| Q34 | Taking a share back? | `share.delete` on Owner and Manager; the sharer always for their own |
| Q35 | Users deleting their account? | A recorded gap; `user.delete` reserved |

## Still to confirm before Phase 1

Two simplifications follow from the decisions above but were never asked directly:

- **Role inheritance (`Role.parentId`) goes.** Owner, Manager and Cashier are flat copies; nothing in
  the requirements needs a role to inherit another. Removing it deletes the hierarchy walker.
- **Per-store roles go.** Today a member can hold a different role at each store
  (`MembershipLocationScope.roleId`). In the new model a member has **one** role plus a set of stores,
  and per-store differences are expressed as store-limited grants.
