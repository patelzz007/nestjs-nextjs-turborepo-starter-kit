## 1. Why `pnpm ci:local` takes so long

### What it costs

I measured each step of a full run from the last green run (before any change):

| Step | Time | Why |
| --- | --- | --- |
| Unit tests (`turbo run test --concurrency=1`) | 7 m 56 s | admin 190 s, merchant 58 s, web 44 s, API 46 s, mobile 44 s, ui 33 s |
| API e2e (`test:e2e`) | 8 m 18 s | 93 files, strictly one after another |
| Browser job (build + seed + both Playwright suites) | ~2 m | builds the API, web and admin, then drives Chromium |
| Everything else (lint, typecheck, build, audits, seeds, RLS, tenancy suites) | ~3 m | mostly cached |

So two steps were about 70 % of the run.

### Root causes

1. **The web, admin and merchant unit suites ran one test file at a time.** Their
   `vitest.config.ts` had `fileParallelism: false`, added in September with no recorded reason.
   On a 10-core machine, admin's 227 files ran on one core for 190 s. (Running workspaces one at a
   time, `--concurrency=1`, is deliberate and documented. Each runner already uses every core,
   so that setting stays.)
2. **Two API e2e tests sent thousands of requests one at a time.** The rate-limit "flood" tests
   send `THROTTLE_DEFAULT_LIMIT` requests (and five times that for the pre-auth limit), each a
   full request with its audit row. Your `apps/api/.env` sets `THROTTLE_DEFAULT_LIMIT=600`,
   so locally that was 3,000 + 600 requests and 70 s for two tests.
3. **The API e2e suite is serial by design.** Every file boots its own Nest app against one
   shared database, so files cannot run side by side. About 230 s of the 495 s is that
   per-file boot (importing the module graph and creating the app), not tests.

### What I changed

- **Unit suites run their files in parallel.** I removed `fileParallelism: false` from
  `apps/web`, `apps/admin` and `apps/merchant`. Before turning it on I ran each suite 4 times
  with parallelism on: 12 of 12 runs passed. Result: admin 190 s → 48 s, merchant 58 s → 15 s,
  web 44 s → 18 s. **`pnpm run test` went from 7 m 56 s to 4 m 26 s.**
- **The rate-limit e2e files pin small limits for their own app.** What they prove (a 429
  exactly at limit + 1, and the right throttler answering) does not depend on the number.
  Each file sets its limits with `vi.hoisted` + `vi.stubEnv` before its app's config is parsed
  and restores them afterwards. It pins all three limits (strict 30 and webhook 120, the shipped
  defaults, and default 150), so a developer's `.env` can no longer change what the tests send.
  A new first test in each file checks that the default limit stays above every route policy's
  own limit. If it didn't, the default throttler would answer the 429 and the test would prove
  the wrong thing (that is how my first attempt with a limit of 20 failed). **80 s → 22 s.**
- **The summary now shows each step's duration and the total**, so the slow step is visible
  without reading the log (`packages/tooling/scripts/lib/format-duration.mjs`, tested).

### Result

**A full `pnpm ci:local` now takes 17 m 26 s, down from about 23 minutes**, with every job passing
(details at the end). The summary now shows where the remaining time goes:

| Step | Now |
| --- | --- |
| API e2e (`e2e:api`) | 7 m 18 s |
| Unit tests | 3 m 56 s |
| Development seed, e2e database | 1 m 42 s |
| Development seed, browser database | 1 m 41 s |
| Everything else | ~3 m |

### What is left, and a recommendation

**The seeds:** the development seed runs twice, once for the e2e database and once for the
browser job's, at about 1m 40s each. The browser job could clone the already-seeded e2e database
instead (`CREATE DATABASE … TEMPLATE …`), saving ~1.5 minutes. I left this alone: the
e2e suites change that database before the browser job starts, so cloning it would mean taking a
clean snapshot right after seeding, and that is part of the same database-per-copy work below.

The API e2e suite is still about 7 minutes, almost all per-file app boot. The proper fix is to
run its files in parallel, each Vitest worker against its own copy of the seeded database
(`CREATE DATABASE … TEMPLATE …` is near-instant in Postgres), with its own BullMQ prefix and
Redis namespace. That should take it to about 2 minutes. I did **not** do this overnight. It
changes how every e2e file gets its database and queues (and the CI job too), and any file that
quietly depends on the previous file's data would only show up as a flake. That deserves a
reviewed change of its own, not a 3 a.m. one. Say the word and I will do it next.

**About running `ci:local` from a git hook:** even at ~10 minutes it is too slow for a hook,
and a hook that slow gets bypassed with `--no-verify`, which the repo forbids. The usual split is:

| Hook | Runs | Time |
| --- | --- | --- |
| pre-commit | `oxfmt --check` + `oxlint` on staged files only | seconds |
| pre-push | `turbo run lint typecheck test --affected` (only workspaces changed since `origin/main`) | 1–3 min |
| before opening a PR | `pnpm ci:local` | full run |

The repo has no husky today. I have not added it, because hooks change every contributor's
workflow and that is your call. Tell me which of these you want and I will wire it up.

## 2. Why a unit test passes in `pnpm run test` but failed in `ci:local`

Both run the **same command** (`turbo run test --concurrency=1`, same environment, Turborepo
cache off for tests). Nothing about `ci:local` itself changes the tests. The difference was the
machine, not the command.

The failing tests (web and merchant analytics, merchant API keys) render a component that
loads through `next/dynamic`. In Vitest, the first load of that chunk is Vite transforming its
module tree on demand. The test then waits for the component with Testing Library's default
**1-second** timeout. On an idle machine the transform finishes in time. On a busy one (another
suite, a build, the browser stack, a dev server) it does not, and the test fails. So the test
had a hidden dependency on machine speed, and whether `ci:local` happened to run on a busy
machine decided the outcome.

**Fix (at the cause):** the tests load the lazy module once in `beforeAll`, so every render
resolves it from the module cache and no assertion depends on how fast the machine is. That was
done yesterday for the three failing tests. Tonight I searched for every other test with the same
pattern and found four more that had not failed yet but would have:

- `packages/ui`: `chart.client-only.test.tsx`, `time-series-chart.client-only.test.tsx`
- `packages/client`: `document-preview-dialog.client-only.test.tsx`, `image-crop-dialog.client-only.test.tsx`

They now preload too. That matters more now that the app suites run files in parallel,
which makes the machine busier. The rule is written down in `docs/technical/operations/ci.md`
("Unit tests").

## 3. Why the log said 4 pm when it was midnight in Malaysia

The transaction log (`logs/transactions/*.txt`) wrote every time in **UTC**. 16:30 UTC is 00:30
in Kuala Lumpur (UTC+8), so the log was right but unreadable for you. Day files also rolled
over at UTC midnight, so your evening landed in "yesterday's" file.

**Fix:**

- New setting **`TRANSACTION_LOG_TIME_ZONE`** (an IANA zone such as `Asia/Kuala_Lumpur`,
  validated at boot). It defaults to the server's own zone (`TZ`, else the OS setting), so on
  your laptop it is Kuala Lumpur time with no configuration.
- Every entry shows the wall-clock time **with its UTC offset**, so it is both readable and
  exact: `2026-10-27 00:30:00.079 +08:00`. Daylight saving, half-hour zones and negative
  offsets are handled and tested.
- Day files run from midnight to midnight **in that zone**, and retention counts in that zone too.
- **Production note:** a container without `TZ` runs in UTC, so set `TRANSACTION_LOG_TIME_ZONE`
  in production to the zone your operators read logs in (documented in `.env.example`,
  `docs/technical/operations/transaction-log.md` and ADR 064).

Today's file, `transactions-2026-10-26.txt`, was written under the old UTC rule. New entries go
to the file for the local day. The NestJS console logger already printed local time, so it is
unchanged.

## 4. API ready in under 900 ms

`🚀 API ready in 1399ms` on your machine; **1090 ms** on mine with the same build. A CPU profile of
the boot showed where it went:

| Phase | Before | Where the time went |
| --- | --- | --- |
| Nest app created | 186 ms | dependency injection, module graph |
| **Swagger mounted** | **543 ms** | building the OpenAPI document: every route, every zod schema converted |
| Server listening | 358 ms | route registration, Prisma's query compiler, Redis/BullMQ connects, schedulers |

Inside the Swagger build, much of the work was repeated:

- **The error envelope was converted about 1,300 times.** The 319 operations document `4XX` and
  `5XX` with `ApiErrorResponseDto` (646 references). Swagger asks a DTO class for its properties on
  every reference, without caching, and also calls the factory of its nestjs-zod parent class, so
  each reference re-ran zod → JSON Schema twice. Now `ApiErrorResponseDto` converts once and hands each reference its
  own copy (`structuredClone`, because Swagger edits what it receives).
- **Shared request schemas were converted again on every route** (for example the
  `{ tenantSlug }` params shared by every tenant route). `zodToOpenApi` now caches each schema's
  conversion per direction (input/output) in a `WeakMap`, again returning a fresh copy per caller.

That cut the document build from ~550 ms to ~285 ms. The document itself isn't needed to serve
a single API request, only to view the docs. So it is now **built on the first docs request**
(Swagger's own document-factory support) and kept for every later one. The docs routes are still
registered before `listen`.

**Result:** API ready in **~515 ms** (5 runs: 492–522 ms), down from 1090 ms. That is a 53 %
cut, which would put your 1399 ms at about 660 ms. Peak heap at boot also fell from ~290 MB to
~220 MB.

**Effect on request performance:** none on API requests. Warm `/health` answers in 5–18 ms, as
before. The first docs page load after a restart takes ~0.34 s (the build), later loads
0.03–0.05 s. In production the docs are off by default, and SuperAdmin-only when on. The
document is unchanged: `test/openapi-artifact.e2e-spec.ts` compares it byte for byte with
`docs/generated/openapi.json`, and that passes.

# Follow-up, 2026-10-27 afternoon: your three answers

## A. API e2e in parallel (445 s → ~115 s)

**How:** test files now run in parallel, each Vitest worker on **its own copy of the database**.

- The e2e global setup (`apps/api/test/global-setup-e2e.ts`) copies `DATABASE_URL`'s database once
  per worker with `CREATE DATABASE … TEMPLATE … STRATEGY FILE_COPY`. That takes ~0.25 s for the
  seeded development scenario; the default WAL-logged copy took 5.9 s.
- Each worker reads its copy from `VITEST_POOL_ID` (`test/setup-env.ts`). The copies are dropped
  when the run ends.
- Every worker also gets its own BullMQ prefix and Redis namespace inside the run's
  (`<prefix>:w<n>`). Workers share Redis, so without this one worker could run another's jobs
  against the wrong database, or trip its login-attempt / rate-limit counters. The run's
  existing purge still deletes every worker's keys.
- **Workers:** half the cores, at most 4 (`E2E_MAX_WORKERS` overrides). `--no-file-parallelism`
  still runs one file at a time. On a 4-vCPU CI runner that means 2 workers.
- **Side benefit:** the suite no longer writes to the database it is pointed at, only to the
  copies. Run against your dev database, it now leaves your real GitHub link and data alone.

**What I checked for**, because only these could break when files run side by side:

- **Shared rows:** fixed by the per-worker copies.
- **BullMQ jobs and Redis keys:** fixed by the per-worker prefix and namespace.
- **Ports:** the one test that listens uses port 0.
- **Cluster-wide Postgres roles:** created idempotently, or with random names.
- **Transaction-log files:** whole-entry `O_APPEND` writes, already safe across processes.
- **Kafka / RabbitMQ:** the API only produces; every consumer is BullMQ.

**Results** (throwaway database, migrated and seeded from scratch):

| Run | Files / tests | Time |
| --- | --- | --- |
| Before (one file at a time) | 93 / 615 | 445 s |
| Parallel, run 1 | 93 / 615 passed | 117 s |
| Parallel, run 2 | 93 / 615 passed | 114 s |
| Parallel, run 3 | 93 / 615 passed | 118 s |
| Tenancy, RLS, single-tenant, single-tenant RLS | all passed | — |

- **Peak Postgres connections:** 42 (the limit is 100).
- **Cleanup:** after every run, no worker database was left behind and the run's Redis keys were
  gone.

**One new requirement:** Postgres can only copy a database while nothing else is connected to
it. With your dev API running, `pnpm test:e2e` against the dev database waits 15 s, then stops
and names what is connected ("stop `pnpm dev`"). CI and `ci:local` use their own idle throwaway
databases, so they are unaffected.
