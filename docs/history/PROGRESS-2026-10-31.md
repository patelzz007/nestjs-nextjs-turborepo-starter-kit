## 1. ELI5 — what got built

- **Shops can message their customers.** A merchant writes a message (bold, lists, tables, a code, one button) and picks who gets it: all their customers, or just the people they tick. They pick when (now, a set time, or 9 a.m. in each customer's own time zone). Customers see it in the app's bell, by email and on their phone, and can report it. Too many reports pause it; repeated abuse switches the shop's messaging off.
- **Private rewards.** A merchant can give a reward to chosen customers only. Everyone else can't see it or claim it, and doesn't even learn it exists. The chosen customer sees a "Just for you" badge.
- **Notification settings.** Everyone can choose what reaches them and where, set quiet hours and a digest, turn offers from each shop on or off, leave a shop, and remove old phones.
- **Rate limits and cache screens.** Admins can see who is being refused for going too fast, give a shop a bigger allowance for a while, and see and flush the cache. When someone is refused, the app now says "Try again in 40 seconds" instead of a vague error.
- **Mobile.** The bell opens a real inbox, with settings and "turn on notifications" (it explains before the phone asks). Phone notifications work once Firebase is configured, and tapping one opens the inbox. At the till, after scanning a customer's QR, you see exactly what was sent and received: request headers (API key hidden), request body and response body.
- **Scan from gallery.** Both QR scanners (Google's ML Kit and our camera scanner) can read a QR from a photo, in this repo and in expo-boilerplate.

  Activity, Offers…) with a picture and a sentence: "In the app and by email", or "Off". Tap a row to see
  its switches.

  and/or platform staff. A message to everyone needs a second person to approve it.

## 3. How to test it from the front end

Accounts (seed): customer `alice.johnson@example.com / Alice@123`, customer `bob.smith@example.com / Bob@123`,
merchant owner `brew.owner@kl-rewards.demo / BrewOwner@123` (KL Brew & Bean), admin
`superadmin@example.com / SuperAdmin@123`. Mailpit inbox: http://localhost:8025.

### Notifications and broadcasts

1. **Merchant** → sign in as the Brew owner → sidebar **Customers → Broadcasts** → **New broadcast**.
2. Title "Weekend specials"; write a message using the toolbar (bold, a list, **Insert table**, a code block, **Add a button** with an `https://` link). Try an `http://` link: it is refused.
3. **Who gets it** → "Customers I pick" → search "alice" → tick Alice. The live count reads "1 customer will get this".
4. **How and when** → keep "As soon as I send it" → **Send**. You land on the broadcast's page; within a minute the status goes Scheduled → Sending → Sent and the results table fills in.
5. **Web** → sign in as Alice → the bell shows it → **Notifications** → **Read the full message** (table, code, button with its real domain) → **Report** → pick a reason.
6. **Mailpit** (http://localhost:8025): Alice's email copy, with an unsubscribe link. Open it → **Unsubscribe**: the page says exactly what stopped.

8. **Admin** → **Emails → Broadcasts**: the broadcast, its message, and Alice's report → **Uphold** (a strike), **Dismiss** or **Resume**.
9. **Limits**: send 5 broadcasts in a week. The 6th is blocked ("You've sent 5 broadcasts this week"). In admin **Operations → Rate limits**, set an override for KL with policy "Broadcasts per week" = 10 and you can send again.
10. **Mobile** → bell → inbox (same notice, rich body, report) → **Notification settings** → **Turn on notifications** (primer, then the OS dialog). With Firebase set up, the next broadcast arrives as a phone notification; tapping it opens the inbox.

### Rewards for chosen customers

1. Merchant → **Rewards → Create New** → **Who can claim** → "Chosen customers" → pick Alice → submit, then approve it in admin (reward review).
2. Web as **Alice**: the reward shows with **Just for you**. Web as **Bob**, or signed out: it isn't in the list, and its link answers "not found".

### Rate limiting

1. Web sign-in: enter a wrong password repeatedly. After the auth limit, the form says **"Too many requests. Try again in N seconds."**
2. Admin **Operations → Rate limits**: that policy's refused count rises, your IP appears (masked) under "Refused most" with **Penalised** once the penalty kicks in, and **Lift penalty** lets you sign in again.
3. Tenant override: set "Tenant API traffic" for KL (e.g. 1/s, burst 2) and click around the merchant console quickly to see the 429 message. Remove the override afterwards.

### Distributed cache

1. Admin **Operations → Cache**: browse the web marketplace and reward pages a few times, then refresh. The hit ratio and entries rise (it auto-refreshes every 15 s).
2. **Flush** a cache, or **Flush one tenant** with a reason: entries drop, and the next read rebuilds them (the audit log records it).
3. Stop Redis (`docker compose stop redis`): the page shows **"Redis is not answering"** and pages keep working from the database. Start it again afterwards.

### Mobile till: request/response and scan from gallery

1. Mobile → drawer **Till** → pair with a code from merchant **POS terminals**.
2. Scan a customer's reward QR (web wallet → a claimed reward). Under the result, **What the till sent** shows request headers (`X-API-Key` cut short), the request body, and the response body. Each block can be copied.
3. Take a screenshot of a reward QR → **Scan from gallery** → pick it: the same flow runs. A photo without a QR says "No QR code found in that photo".
4. expo-boilerplate → **Settings → QR scanner** → **Scan from gallery**.

## 5. Deviations and decisions (also in the ADRs)

| Decision | Why |
|---|---|
| editorcn **ported**, not installed through the shadcn CLI | Its registry item is ~180 KB, mostly features ADR 073 turns off (colours, highlight, embeds, alignment) plus copies of primitives we already have. | Editor parts render only once the editor exists | Found by testing: otherwise every toolbar button stayed disabled until the first keystroke. |
| A 429 without a stated wait | Web and mobile show the API's own (client-safe) message; admin keeps its generic copy. |
| The flaky audit-trail e2e test | Root cause: other spec files write audit rows in parallel on the same DB, so "the channel stays silent" can't be guaranteed. The test now checks the same rule (reading the log doesn't trigger a signal) using that read's own correlation id. |
