## Migration baseline and the CI Build job

| Item | What changed |
| --- | --- |
| Migration baseline | The owner re-migrated and re-seeded, so `migrations-baseline.json` now names `20261106020237_init`, the same value as the migrations folder and `_prisma_migrations` in the dev database. |
| CI Build hang (run 42059018871) | The runner received a shutdown signal 5 minutes in. It stopped logging, but GitHub showed the job as running until the 30-minute limit plus a 5-minute grace. |
| Build time limit | Lowered from 30 to 15 minutes. A normal build takes about 6, so a lost runner now frees up sooner. |
| Build memory | `turbo run build` now uses `--concurrency=3`. Measured on a 10-core Mac with warm Next.js caches, the sum of process memory peaked at 22.66 GB with no limit and 10.66 GB with the limit. The runner has 16 GB. |

Why the runner shut down is not proven. GitHub keeps no memory record for the run, and 13 of the last 14 Build runs did not hit this. High memory use is the likely cause, and an outage on GitHub's side is also possible.

**Mobile light contrast:** the light theme added at 04:43 put the link blue (`#2563eb`) on the raised surface (`#e5f0fe`) at 4.49:1, under the 4.5:1 minimum. The raised surface is now `#e6f1fe` (4.52:1). The link keeps the owner's Tailwind blue-600. expo-boilerplate got the same change.

**Analytics connection limit:** the merchant dashboard opens about ten transactions at once, and only the raw SQL aggregates went through `AnalyticsSqlRunner`'s limiter. The reward-activity and sales repositories skipped it, so on a busy machine a read could wait past Prisma's 5-second `maxWait` and return a 500 (`P2028`). Both repositories now read through the runner, so all analytics reads in a process share one limit. A regression test in `tenant-transaction-session.e2e-spec.ts` failed with that exact error before the limit and passes with it.

**Drain test flake:** `bullmq-worker-drain.service.spec.ts` built a real BullMQ `Worker`, which connects to Redis even with `lazyConnect`, then cut it off mid-handshake. The resulting log could arrive after Vitest had closed, which failed the run with all tests passing. The test now uses a `Worker` stand-in with only `close`, the one thing the drain calls.

**Sidebar snapshot:** `sidebar (dark)` failed twice with the same 53 pixels: glyph edges on two text rows of the first example, with no layout or colour change. No code in that example, its components or the web theme changed, so the cause is not proven. Only `sidebar-dark.png` was replaced, with the Docker suite's own output. The tolerance is unchanged.

| Found on the way | Fix |
